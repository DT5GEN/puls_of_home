# CLAUDE.md: домовой статус-портал «Пульс дома»

Этот файл читает Claude Code при каждом запуске в корне репозитория. Здесь правила проекта. Детальное ТЗ лежит в `docs/TZ_dom_status.md`, история решений в `docs/HISTORY.md`, схема дома генерируется в `docs/dom_draft.json`, текущий промпт этапа в `docs/prompts/`.

Перед началом работы в новой сессии прочитай `docs/HISTORY.md`: там контекст проекта и принятые решения.

## Что за проект

Внутридомовой портал для жильцов одного дома (позже группы домов). Жильцы видят статус дома на 3D-модели: цвет окна отражает состояние квартиры. Заявки, замечания и предложения проходят через подтверждение по правилам из ТЗ (раздел 5а). Есть архив по категориям и общий чат дома. Публичного доступа без входа нет.

## Текущий этап

Этап 1: модель данных, переходы состояний заявки, видимость полей, лимит мест, эскалация аварий, сид из JSON, тесты. Интерфейса, 3D, чатов, входа и внешних API на этом этапе нет. Не добавляй их без явной просьбы.

3D-прототип лежит в `docs/prototype/` как референс для будущего фронтенда. Он не часть этапа 1.

## Стек

- Node.js LTS, TypeScript с `strict: true`
- PostgreSQL 16 в Docker (`docker-compose.yml`)
- Prisma для схемы и миграций
- Zod для валидации JSON
- Vitest для тестов
- Версии фиксируются через lock-файл. Новые зависимости добавляй только с согласия, и запиши причину в PR.
- Скрипт `tools/gen_dom_draft.py` (Python 3, только стандартная библиотека) генерирует `docs/dom_draft.json`.

## Структура

```
prisma/           схема и миграции
src/domain/       переходы, видимость, места, эскалация, журнал, типы
src/schema/       Zod-схемы
src/seed/         перенос dom_draft.json в базу
tests/            тесты по модулям
tools/            генератор схемы дома
docs/             ТЗ, история, промпты, прототип, схема дома
```

## Жёсткие запреты

- Не добавляй поля с персональными данными: `fullName`, `firstName`, `lastName`, `email`, `phone` (кроме хеша), `passport`, `address` жильца, фото людей. Есть тест, который это проверяет, не обходи его.
- Не меняй структуру `dom_draft.json` без записи в `OPEN_QUESTIONS.md`.
- Не добавляй категории обращений, роли, статусы и типы объектов сверх описанных в ТЗ. Список категорий и состояний зафиксирован в `src/domain/types.ts`.
- Таблица `RequestEvent` только для добавления. Никаких UPDATE и DELETE по ней, даже в тестах и миграциях.
- Закрытие заявки проверяется по `placeScope`: квартира требует подтверждения автора-жильца; общая зона и двор требуют подтверждения модератора другой секции; предложение требует подтверждения автора. Полные правила в `docs/TZ_dom_status.md`, раздел 5а. Не добавляй обходных путей, включая флаги и тестовые хелперы в продакшн-коде.
- Не используй `new Date()` внутри доменной логики. Время передаётся аргументом, чтобы тесты были детерминированными.
- Не выдумывай поведение, которого нет в ТЗ или промпте. Неоднозначность записывай в `OPEN_QUESTIONS.md` и выбирай безопасный вариант по умолчанию.

## Значения по умолчанию

- `ESCALATION_HOURS = 24`
- `seatLimit = 2` на квартиру
- `apartmentsTotal = 209` (по данным), фактическое число квартир в модели вычисляется
- Наблюдатели из других домов выключены (`nablyudateli_vklyucheny: false`)

## Правила кода

- Бизнес-логика только в `src/domain/`. Прямые запросы к базе из доменных функций не делай, работай через репозитории или передавай данные аргументами.
- Функции переходов, видимости и цвета чистые, без побочных эффектов, кроме явных записей через репозиторий.
- Ошибки запрета возвращаются как `{ allowed: false, reason }` с причиной на русском. Исключения используй только для программных ошибок.
- Комментарии в коде на русском, имена переменных и функций на английском.
- Все идентификаторы объектов: uuid как первичный ключ, `kod` отдельно и уникально. Связи только через uuid.

## Тесты

Обязательны для любой доменной логики. Перед тем как отметить задачу готовой, запусти `npm test` и проверь, что все тесты проходят.

Обязательные группы (полный список в промпте этапа):
- переходы состояний: разрешённые и запрещённые
- закрытие без требуемого подтверждения
- журнал событий не меняется
- видимость по типу заявки и роли
- наблюдатель при выключенном флаге не видит ничего
- цвет окна в четырёх случаях
- лимит мест, включая параллельное создание
- эскалация по порогу с фиктивным временем
- сид идемпотентен
- в схеме нет полей с персональными данными

Не удаляй и не отключай тесты, чтобы проходила сборка. Если тест падает, исправляй код или записывай расхождение с ТЗ в `OPEN_QUESTIONS.md`.

## Git и процесс

- Работай в отдельной ветке `feature/<короткое-имя>`. Прямых коммитов в `main` не делай. Исключение: первая выгрузка документов владельцем (2026-10-21).
- Один PR на одну задачу. В описании PR укажи, какие пункты ТЗ закрыты, что не сделано и какие тесты добавлены.
- Коммиты небольшие, с понятным сообщением на английском в повелительном наклонении (`Add seat limit check`).
- Перед открытием PR запусти тесты и линтер. Не открывай PR с падающими тестами.
- Секреты только в `.env`, файл в `.gitignore`. Не коммить `.env` и не печатай его содержимое в вывод.

## Что делать при неясности

1. Проверь ТЗ, промпт этапа и `docs/HISTORY.md`.
2. Если ответа нет, выбери значение по умолчанию из раздела выше.
3. Запиши вопрос и принятое решение в `OPEN_QUESTIONS.md` с датой.
4. Продолжай работу, не останавливаясь на каждом вопросе.

Если нужно изменить стек, структуру или правила из этого файла, предложи изменение отдельным PR с обоснованием. Не меняй `CLAUDE.md` вместе с кодом без явного указания.
